# 共有アプリの設計原則

共有アプリ（`app.json` を持つリポジトリ）が守っている不変条件と、**それを守っている場所**。

この文書は決定の記録ではない。決定は [`plans/feat-shareable-collections.md`](../plans/feat-shareable-collections.md)
の **D1–D10** にあり、個々の実装理由は `../mulmoserver/firestore.rules` と
`server/backends/sharedApp/*.ts` のコメントが持っている。ここに書くのは、それらを読む前に
知っていないと**設計を静かに壊す**ことだけ — 壊れても typecheck もテストも CI も通る種類の話である。

新しいキー・新しいビュー・新しい操作を足す前に、この 11 個に照らすこと。

---

## 0. 一行で

> **宣言はレビューできる。強制はルールにある。著者のマシンは実行経路にいない。**

3 つのうち 1 つでも崩れると、残りの 2 つは意味を失う。以下はその展開である。

---

## 1. 著者のマシンは、公開されたアプリの実行経路にいない（D7）

publish が終わったら、著者の MulmoTerminal を落としてもアプリは動き続ける。これは性能上の
好みではなく、**アプリを人に渡せるかどうか**を決める性質である。

守られている場所: **どこにも自動の門番はいない。** D7 は不変条件だが、コードがそれを検査する
仕組みは無い — 破るのは常に「ホストで 1 本だけ動かす」という便利な近道である。監視点は 4 つ
（`plans/feat-shareable-collections.md` の「D7 が漏れうる箇所」）:

1. **メール送信をホストで監視しない。** Trigger Email 拡張（`apps/{aid}/mail`）の採用は好みではない
2. **publish のペイロードが完結していること。** 実行時にディスクを見る経路が 1 本でも残れば嘘になる
3. **`ref` を辿る計算はビューの親が解決してから渡す**（ビュー側で解決させない）
4. **匿名トラフィックは既定で単発取得。** ライブは宣言で選ぶもので、既定ではない

**破れ方**: 「今は自分しか使っていないから」で足したホスト側の 1 本は、他人に渡した瞬間に
初めて壊れる。壊れたことは著者には見えない。

---

## 2. ホスト側の門番は診断であって、権限ではない

MulmoTerminal の検査（`records.ts` の移行ゲート、`scopedFields.ts` のフィールド名検査、
`publicForm.ts` の公開入力検査）は**著者の手元でしか走らない**。攻撃者の手元では走らない。

だから同じ保証が要るものは、必ず**ルール側にも**書く。`firestore.rules` の `mailBound()` の
コメントが、この原則を一番短く言っている:

> **A LINTER IS NOT A SUBSTITUTE FOR A RULE**（リンターは作者のマシンでしか走らない）

守られている場所: `../mulmoserver/firestore.rules`。ホスト側の検査は
**同じことを早く・読める言葉で言う**ためにあり、保証を持つためではない。

`preview`（ページを実ブラウザで走らせる方）も同じ側にいる。**緑が言っていないこと**が 3 つあり、
どれも黙っているので、報告をそのまま「動く証拠」として渡さないこと:

- **ルールの判定は既定では読んでいない。** `confirm: true` を送ったときだけ、deploy 済みルールの
  答えを読むために**実レコードを書く** — 1 本とは限らず、1 run あたり最大 4 本
  （`LIMITS.writes`、`headlessPreview.ts:261`）。消すのは best-effort で、**消し損ねうる**。
  しかも報告に出るのは**正常に終わった run の、押下ごとの削除結果だけ**である — run が途中で
  落ちたときの掃除（`sweep`、同 `:1049`）は**何も報告せず、自分の失敗も飲み込む**ので、
  残ったレコードはどこにも現れない。存在している間そのレコードは本物なので、
  遷移に束縛された副作用（メール）が走りうる。既定では何も書かないので、宣言が本番の
  ルールに通るかは**未検証のまま**である
- **`change` ハンドラから保存する部品は押されない。** チェックボックスやセレクトは行として
  出てこない — 保留（withheld）とすら言われない — ので、その保存経路は未検証のまま緑になる
- **判定は常に著者の経路のもの。** preview も Collections ペインも著者として書くので、訪問者や
  participant にルールが何と答えるかは、どちらも言わない

一次資料は `server/infra/shared-app-tool.ts` の `manageSharedApp` prompt（ここは要約である）。

**破れ方**: 「publish が拒否するから大丈夫」と書いたルールの穴。publish を通さずに
Firestore へ直接書く経路は常にある（それが Functions を使わない設計の代償である）。
そして**書いていないものは「守られている」と読まれる** — 上の 3 つが prompt にしか無かった間、
外部レビューは preview の緑を検証済みと解釈した（偽のグリーン）。

---

## 3. ルールは数えられない。だから定員は「順位」である

Firestore ルールはクエリを実行できない。`count(where status == "approved") < 20` は書けない。

したがって「先着 20 名」は 2 通りのどちらかにしかならない:

- **順位から導く** — `stampField` がサーバ時刻を create で固定し、以後**動かせない**
  （`stampOk` / `stampHeld`）。「先頭 20 行」は読む側の解釈であって、強制ではない。
  繰り上げは操作のたびに計算し直され、通知は飛ばない
- **枠を実在させる** — 20 個のドキュメントを先に作り、申込みがその id を**衝突で**取る（原則 4）

守られている場所: `firestore.rules` の `stampOk()` / `stampHeld()`。stamp は
**writer の create も縛る** — スタッフが代理入力した行を待ち行列の先頭に差し込めない。

**破れ方**: 「定員」を宣言に足して、読む側の表示でしか効いていないのに、強制されていると
説明してしまうこと。どちらなのかを**宣言の言葉で区別する**こと。

---

## 4. 一意性はドキュメント id に置く

「一人一回」「1 枠 1 予約」「1 資産 1 貸出」は、フィールドではなく **id の衝突**として書く。
Firestore の create は id の存在を原子的に判定できる。フィールドは判定できない。

守られている場所: `firestore.rules` の `idOk()`（`auto` / `auth.uid` / `auth.uid+field`）と
`ownRow()`。合成 id は正規表現ではなく**保存値から組み直して**照合する —
uid に正規表現メタ文字が入っても壊れないためであり、`<victim uid>_x` を作って
他人の行の自己編集権を育てる攻撃を止めるためである。

**破れ方**: 「同じ枠を 2 人が取れない」を、読む前のチェックや取引の外の update で実現しようとすること。
2 人が同時に読めば 2 人とも通る。

---

## 5. ルールはフィールドを隠せない。可視性の境界は**ドキュメントの境界**である

読み取りはドキュメント単位である。`public.read` に載せたコレクションは、その行の**全フィールド**が
世界に読める。ブラウザで落として表示しないのは、開示の**後**の話である。

守られている場所: 設計そのもの。実例が 2 つある:

- 名簿向けのページ（`member/*` `roster/*`）と公開の `config/*` が**別のドキュメント**なのは、
  `config/{docId}` が `allow read: if true` だから。1 つの文書の 2 フィールドでは隠せない
- 公開ページの入力フォームは `config/public` という**別の文書**に射影される（`publicForm.ts`）。
  `allow read: if true` の文書なので、**ここに載せたものは全部公開である**。載るのは
  `createFields` のフィールドについて `label` / `type` / `enum` の `values` / `required`、
  それに**ルールが要求するフィールド名** 2 つ（`statusField` と `stampField`）— 訪問者が
  知らなければ書けない値だからで、載っているのは名前であって値ではない。
  逆に `createFields` の**外**のフィールドは名前ごと載らない — `status` の取りうる値や
  査読メモの語彙を世界に配らないため

  つまり境界は「ラベルだけ」ではなく「**入力を描くのに要るものだけ**」である。
  ここに 1 つ足すのは、公開の表に列を 1 つ足すのと同じ重さで判断すること

- アプリ自身の**ページ**も、監査対象ごとに別のドキュメントに置く（`apps/{aid}/member/*` は
  ロールを持つ人、`apps/{aid}/roster/*` は名簿の人）。`config/{docId}` は
  `allow read: if true` なので、受付の画面をそこに置くとアプリの内部語彙 — 状態名・査読メモの
  見出し・担当の付け方 — が世界に出る。そして**射影を分けるだけでは足りない**: participant は
  スタッフ用のドキュメントをパスで直接取得でき、語彙は HTML そのものに書いてある。
  分けるものはルールで分ける（[`plans/done/feat-shared-app-member-view.md`](../plans/done/feat-shared-app-member-view.md)）

> **`config/` に置いたものは、置いた時点で公開されている。名簿向けの HTML をここに置いては
> いけない。** `../mulmoserver/firestore.rules` の `match /config/{docId}` は
> `allow read: if true`（同 `:157-159`）で、ここに publish 状態は**掛かっていない** —
> `public` ブロックの有無も unpublish も、この読みには関係しない。unpublish が
> `config/public` を消すのは**緩和であって不変条件ではない**（消す前に読まれたものは戻らない）。
> 名簿の人に見せるものは `member/*` / `roster/*` に置くこと。

**破れ方**: 個人情報を含む行を「公開の表に出したい」と言われて、注意書きを添えて `public.read` に
足すこと。注意書きは強制ではない。**別コレクションに割る**のが唯一の答えである。

## 6. 状態機械は全員を縛る。writer も、create も

`transitions` を宣言したら、それは投稿者だけでなく **owner / editor にも**効く。そして
**create にも**効く（`initialOk`）。

そうでないと、「pending だけが approve できる」という宣言は助言になり、writer は
**最初から approved のレコードを作れる**。status を消す書き込みも同じ理由で拒否される —
消せるなら「消してから何にでも設定する」で 2 手で機械を迂回できる。

守られている場所: `firestore.rules` の `initialOk()` / `transitionOk()` / `updateWith()`、
そして `selfWriteOk()`（投稿者が触れるフィールドは**現在の status ごと**に宣言される）。

**破れ方**: 「owner は何でもできる」を素直に書いてしまうこと。owner が持つのは**運用の広さ**で
あって、**レコードの整合性の免除**ではない。

---

## 7. `assignee` は書きだけスコープされる。読みは全部見える

役割の非対称は**意図的**である。自分の予約しか承認できないスタイリストも、その日の予定表は
全部見える必要がある。読みまでスコープすると、**誰も働けないアプリ**になる。

守られている場所: `firestore.rules` の `readerOf()`（`assignee` を含む）と
`assignedWriter()` / `assignedBefore()` / `assignedAfter()`。update は**前後の両方**を要求する —
前だけなら同僚の行を自分に付け替えて奪え、後だけなら自分の行を他人に渡しながら書ける。
mail も同じ非対称を持つ（`mailWriter()`）: 承認できない予約の承認メールを送れてはいけない。

**破れ方**: 「スコープされた役割」を一様に読み書き両方へ広げること。安全に見えて、使えなくなる。

---

## 8. 順序が保証である。fail closed の向きを変えない

- **`init` は安全な半分**（`apps/{aid}` の名簿と `appSlugs/{slug}` の予約）。誰にも公開を与えない。
  ここから記録は書けてプレビューは走るが、公開の顔は何も無い
- **publish は `apps/{aid}.public` を最後に書く。** **まだ公開されていない**アプリは、途中で
  落ちても**非公開のまま**残る。**既に公開されているアプリの再 publish は違う** — 古い
  `public` ブロックが最後まで生きているので、途中で落ちれば**開いたまま版が混ざる**。
  それは意図された取引であって事故ではない（下の「破れ方」）。逆向きだと期待しないこと
- **unpublish は逆順。** 権限を先に落とす
- **slug の反転は `public` ブロックの有無に従う。** publish したから公開、ではない —
  名簿だけのアプリで slug が解決すると、**世界から読める予約が aid を配る**ことになる

守られている場所: `server/backends/sharedApp/publish.ts` / `establish.ts` / `unpublish.ts` の
書き込み順（`runWrites`）と、それぞれの冒頭コメント。

**2026-08-16 に半分が消えた。** かつては `deploy` が `staging/{cid}` に書き、publish がそれを
**昇格**させた（「名簿が見た版が出る」という保証）。staging は廃止され、publish は working tree を
そのまま書く（`plans/feat-shared-app-no-staging.md`）。代わりに立つのは `preview` — 著者の手元で、
publish の直前に、実ブラウザでページを走らせる。

**破れ方**: 「公開を先に閉じてから書き換える」方が綺麗に見えること。それは再 publish のたびに
**確実な停止**を作り、失敗すればアプリは**暗いまま**になる。今の順序は「混ざった版で開いている」を
選んでいる — それは**アクセスの変化ではない**（古い `public` ブロックが権限の源のままだから）。

## 9. 取り消せないものが 3 つある。だから `fork` がある

- **`aid`** — コードが発行する UUID。人が選ばない（D2b）
- **`appSlugs/{slug}` の予約** — `allow delete: if false`。解放された名前は、既に配られた URL から
  別のアプリを配ることになる。**予約は `init` で起きる**（2026-08-16 から）ので、捨てられたアプリ
  1 つにつき名前が 1 つ死ぬ。だから予約するのは**著者が書いた名前**であって、コードが考えた名前では
  ない
- **`apps/{aid}` そのもの** — `allow delete: if false`。Firestore はカスケードせず、子文書の
  ルールは全部**親を `get()` してから始まる**ので、親を消すと中身は誰にも読めず誰にも消せなくなる

この 3 つは、**clone したリポジトリが持ってきてはいけないもの**でもある。clone は `app.json` を
そのまま運ぶので、`aid` も `members` も付いてくる。だから `manageSharedApp` の `fork` は
`aid` / `slug` / `owner` / `members` / `aidEnv` / `name` を**落とし**、残りは全部引き継ぐ
（`declare.ts` の `CLONED_APPS_OWN`）。

**破れ方**: 「clone した人も publish すればいい」と考えること。他人の aid に publish しようとして
拒否され、`app.json` を手で消すよう案内することになり、**取り返しのつかない削除**を
一番不慣れな人の手に置くことになる。

## 10. 1 リクエストの評価予算は 1000 式。**その経路を通るアプリが全部**払う

ルール関数は呼び出し箇所ごとにインライン展開される。深い補助関数の連鎖は非自明な経路で上限に達し、
症状は「権限エラー」ではなく `Unable to evaluate the expression…` になる。

払うのは**その述語を評価するリクエストだけ**である。別の操作にしか出てこない条件や、
短絡の後ろにある条件は、通らないリクエストの予算を食わない。だから見積もりは
「機能が重いか」ではなく「**どの経路に載るか**」で決まる — そして共有された経路
（`items` の create / update）に載せたものは、その経路を使う**全アプリ**が払う。

守られている場所: `firestore.rules` の書き方そのもの — **app ドキュメントの `get()` は
ルールごとに 1 回**で、あとは引数で下へ渡す。`appSlugs` の read が
`published == true` を先に見るのは、まさに経路を分けた例である（公開ページの hot path が
`listedIn()` の `get()` を払わない）。

**破れ方**: 正しさだけを見て条件を足すこと。**次にルールへ条件を足すときは、正しさと同じだけ
式数を見ること** — 影響する経路を名指しして、その経路の最も重い宣言で測ること。
そして上限に当たった症状は、機能追加とは無関係な既存アプリに出る。

## 11. HTML は宣言の射影である。真実を HTML に移さない

sandbox の中の HTML は自由に生成してよい（Firestore ハンドルも資格情報も渡らない）。
守るのは「HTML を書かせない」ことではなく、**「HTML に真実を移させない」**ことである。

判定基準はひとつ:

> **宣言を読んでも、このアプリが何をするか分からなくなったら、設計は失敗している。**

そうなると、公開データ・権限・状態遷移・副作用が**レビュー対象から消える**。git で管理される
React アプリに戻っただけで、それはもう新しくない。

守られている場所: View Bridge の分割（親が Firebase を持ち、ビューは受け取った値を描くだけ）と、
公開ビューについては [`plans/done/feat-shared-app-public-view.md`](../plans/done/feat-shared-app-public-view.md)。
公開ビューでは**`event.source` の検証では足りない** — それは「どのウィンドウか」を示すだけで
「人が選んだ」を示さない。書くと決めるのは**親**であり、親が自分で描いた確認を挟む。

メンバー用のページで足りなくなったものが 2 つある:

- **`event.source` は「どのウィンドウか」しか示さない。** sandbox のフレームは自分の browsing
  context を遷移でき、`contentWindow` はそれを生き延びる。しかも load を数える防御は
  **初回パースの最中の遷移**を捕まえられない（元の文書が `load` を一度も発火しないため）。
  だから注入した bootstrap は**レンダーごとの nonce** を名乗り、親はそれに一致する `ready` にしか
  答えない。script 要素は著者の HTML がパースされる前に自分を DOM から外す
- **メンバービューのデータは公開データではない。** 公開ビューには「持ち出せるのは誰でも取れる
  データだけ」と言えた（`public.read` との共通部分しか渡さないため）。ここでは言えない —
  渡すのは氏名・連絡先を含む本物のレコードである。**これは越えられる境界ではない**と判断している:
  ビューを書くのはオーナー、データもオーナーのもの、読むのはオーナーの名簿にいる人で、
  ビューを書かなくてもコレクションの画面から書き出せる。**ただし publish の出力がそう言う**
- **名簿の人の書き込みには確認を挟まない**（[`plans/done/feat-shared-app-member-write.md`](../plans/done/feat-shared-app-member-write.md)）。
  公開側で確認が要るのは、ページを書いた人と責任を負う人が違うためで、メンバー側はそこが逆
  （店のページ・店のデータ・本人のロールが上限）。1 日に何十回押すボタンの前のモーダルは、
  安全性を上げずに使うのをやめさせる。**代わりに、何が起きたかを親が iframe の外に必ず出す** —
  ページは自分の成功について嘘を描けるので、これは省略できる装飾ではない。
  そして意図の語彙は**閉じている**（状態遷移と担当の付け替えの 2 つ、どちらも 1 フィールド）:
  汎用のパッチにしてもルールが権威であることは変わらないが、ページのバグがそのメンバーの
  権限いっぱいまで届き、何が起きたか親が言えなくなる

**破れ方**: 宣言で書けない要求が来るたびに HTML へ逃がすこと。1 回ずつは合理的で、
合計すると設計が消える。**逃げ道を塞ぐのではなく、宣言の表現力を広げる**のが答えである
（→ [今後の拡張計画](../plans/feat-shared-app-platform.md)）。

## 新しい能力を足すときに、先に答えること

一般論のチェックリストではなく、このリポジトリで**実際に踏んだ**ものだけを挙げる。

1. **強制はどこにあるか。** ルールか、ホストの門番か。ホストだけなら、それは診断である（原則 2）
2. **どの経路の式数が増えるか。** 経路を名指しし、その経路の最も重い宣言で測る。
   共有された経路（`items` の create / update）なら、使う全アプリが払う（原則 10）
3. **ルールの deploy が先か。** `mulmoserver` に CI はある — `.github/workflows/pull_request.yaml`
   が `yarn test:rules`（emulator + JVM、`test/rules/*.ts`）を PR ごとに回している。**無いのは
   deploy の方**で、ルールは手で出すものであり、**deploy 状態はどのリポジトリにも
   記録されない**。緑の CI はルールが正しいと言うだけで、それが本番に出ているとは言わない。
   ルールが出る前に宣言を publish できると、著者には成功に見えて訪問者は壊れた
   ページを見る。「古いルールでは fail closed になる」だけでは足りない — **publish を拒否する**か、
   runtime を先に出すか、どちらかを決めてから足すこと。
   **2026-08-18 に「拒否する」側を入れた**: deploy 済みのルールの版は
   `deployment/capabilities`（`../mulmoserver`、誰でも読め・どのクライアントも書けない）に
   手で記録し、publish がそれを読んで**遅れている deployment には書かない**
   （`server/backends/sharedApp/deployment.ts`）。記録が**無い**場合は拒否ではなく報告である —
   ホスト側の門番は診断であって権限ではない（原則 2）し、記録を書くまではどの deployment にも
   無いのだから、無いことを理由に止めると全部止まる。**記録するのは deploy した人の手作業**で、
   そこだけは依然として自動化されていない
4. **既に live なドキュメントから持ち越されるキーがあるか。** `projectPublish` は `owner` と
   `previousPublished` を既存の文書から引き継ぐ。射影が知らないキーの扱いを確かめること
5. **live なレコードがあるとき、その宣言は変えられるか。** 排他や鏡（mirror）の結び付きは、
   1 行でも残っていれば**凍らせる**。変えて publish し直すと、古い行が指す先が変わる
6. **宣言とスキーマの**組**が検査されているか。** ロールやフィールド名は `app.json` にあり、
   その名前が実在するかは**スキーマ**にしか無い。両方を通した組を見るのが `scopedFields.ts` で、
   これは宣言ゲートが原理的に見られない半分である
7. **半端に終わった run が残す状態は、次の run で直るか。** `runWrites` はどの書き込みの後でも
   止まる。かつては deploy と publish の 2 段だったので「揃っていない組」を publish が
   見分ける必要があり、run ごとの識別子を載せていた。1 段になった今の答えは単純で、
   **もう一度 publish すれば全部が同じ run から書き直される**こと
8. **否定のテストと同じ数だけ、肯定のテストがあるか。** 全部を拒否するルールは、
   意図した方針が動く証拠にならない

---

## 明示的に「できない」と言うもの

境界を曖昧にするより、断ったほうが宣言の意味が保たれる。

- **アプリごとのサーバコード**（Functions、アップロードされたハンドラ）。プラットフォームが
  持つ固定の効果（メールキュー）を**選ぶ**ことはできる
- **ルールによる件数の判定**（原則 3）と**フィールド単位の秘匿**（原則 5）
- **任意区間の重なり判定**（「このシフトと重なる予約があるか」）。離散的な枠 id なら書ける
- **秘密投票。** 表示で投票者を隠すのは秘密投票ではない。信頼された匿名化が要る
- **著者のマシンや訪問者のブラウザが開いていることに依存する定期処理**（原則 1）
