### F-01 が半分誤りである根拠（再提出されたらここを指す）

`server/backends/sharedApp/publish.ts:246` の `stillOpen()` が、**publish 中のすべての中間書き込みに
「今 live な `public` ブロック」を載せ直している**。だから既に開いているアプリは再 publish の間ずっと
開いたままで、レビューの言う「意図的な停止」も「途中失敗でアプリが暗いまま残る」も起きない。

Codex がそう読んだのは、同ファイル冒頭コメントの **19–21 行目が古い**からである
（「再 publish は `public` の無い瞬間を通る」）。23–30 行目は正しい挙動を書いていて、**同じコメントの中で
自己矛盾している**。レビューは古い方を信じ、その上に重大度を積んだ。

## やらないこと

**不変リリース + 原子的な `activeRelease` ポインタへの作り替え（F-01 本体）。**

- 動機として挙げられたシナリオ（再 publish でアプリが暗くなる）は**起きない**（上記の検証）。

  stale ではなく **DARK** を残す — アプリを使う人にとって明確に悪い。
- 系全体で最も危険な操作を、実在しない不具合を理由に大きく書き換えることになる。

やるとしたら、7 が入って**リリースに版が付いた後**である。版の無いリリースを原子的に切り替えても、
切り替えた先が対応しているかは誰も知らない。

**役柄ごとの emulator E2E（F-04）。** 妥当だが本計画とは別物で、規模も別。
`plans/feat-shared-app-platform.md` 側に置く。

**`previousPublished` の改名（F-03）。** 挙動は正しく、コードは rollback を主張していない。
7 で完全なリリースを保持するようになれば、この語は自然に決着する。それまで触らない。

Firestore は cascade しないので `collections/*/items` / `config/*` / `member/*` / `roster/*` が
**永久に読めず消せない孤児**になる（`get(apps/{aid})` が評価エラーになり、すべてが fail-closed に
落ちる）。ルールの `allow delete: if false` はクライアントに対してこれを防いでいるが、
**Admin SDK を持つホスト（＝著者自身）には掛からない**。

そして「詰まったので `aid` を消してみる」は、項目 14 が指摘したとおり**エージェントがまさに
手を伸ばす回復手段**である。項目 14 で `partial: true` の返答文面を触るとき、および skill の
「never edit `aid`」の隣に、**この 1 行**を足す。項目 14 に同乗。

---

### §11 の見落とし — レビューは `package.json` を 3 つ並べて読まない

Muse は §11 で「3 者のピンは人間だけが留めている」と正しく書きながら、**実際に今ズレている**
ことに気づかなかった（`mulmoserver` は `^0.8.0`、MT は 0.9.0）。4 本のうちこれを掴んだのは
Grok の H2 だけである。

これは責める話ではなく、**項目 7 の 5 番が引き受けるべき仕事の定義**である: 3 リポジトリの
依存を突き合わせるのは、読み手（人でもモデルでも）ではなく CI の仕事である。読めば分かる
ことでも、**4 本のレビューのうち 3 本が見落とした**という事実の方が、機械に渡す根拠として強い。

### 4 本目から足す順序

既存の順序（項目 1–5 と、3 本目から足した分）は変えない。上に足すのは:

- **項目 2 の PR の優先度を上げる**: 項目 3 は「誤字の修正」ではなく、**外部レビューを 2 回
  誤らせた 1 行**の修正である（M-1）。この PR を次のレビューが走る前に出す。
- **項目 14 に同乗**: 項目 16（`apps/{aid}` を消すと孤児になるという 1 行）。
- **項目 7 の 5 番に吸収**: 項目 15（共有フィクスチャ）。単独では出さない。
- **項目 7 の 1 番の格上げ**: `mulmoserver` の 0.9.0 bump は衛生ではなく、
  ラウンドトリップ試験 2 本が古い射影を検証しているという**証明の穴**である（項目 7 の現状に反映済み）。

**4 本を通しての結論は 3 本目から変わらない。** 新規の不具合を出したのは Codex（4 件）・
Grok（5 件）・Muse（1 件）で、Gemini は 0 件。だが 4 本すべてが、こちらの一次資料の誤りを
**そのまま自分の結論として持ち帰った**（F-01・G-1・M-1）。項目 2 と項目 3 を最初に出す理由は、
4 本目を見ても変わらない — むしろ**震源が `publish.ts` のコメントだけでなく、原則の文書にも
あった**ことが分かった分だけ強くなった。
