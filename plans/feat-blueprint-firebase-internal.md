## 前提: 共有アプリとは別物

`server/backends/sharedApp/` の共有アプリは、**こちらが持つ** Firebase（`../mulmoserver`）の上で宣言を動かす。
設計図パックは、**利用者自身の** Firebase プロジェクトを作ってアプリを組み立てる。

- 流用するもの: ルールを「既定で拒否、宣言で開ける」形で書く知見と、`docs/shared-app-principles.md` の「門番は診断であって権限ではない」という原則
- 流用しないもの: 共有アプリの宣言の語彙・mulmoserver の rules・`SHARED_APP_ACTIONS`

混ぜると「共有アプリの制約が利用者のアプリにかかる」か「利用者のアプリの都合が共有アプリの rules に入る」かのどちらかになる。

## パックの形式

基盤パックと用途パックを分け、実行時に組み合わせる。基盤と用途をかけ算で全部作ると、同じ内容の写しが増えるため。

```
blueprint-firebase/                   基盤パック
  manifest.json                       種別・名前・版・必要な CLI・必要な認証情報・組める用途
  spec/overview.md                    この基盤で決めるべき項目の雛形
  security/checklist.md               この基盤で必ず詰める点
  infra/                              firebase.json, firestore.rules, firestore.indexes.json, storage.rules
  skills/<step>/SKILL.md              工程ごとのスキル
  checks/<step>.(sh|ts)               工程の完了判定。終了コードで判定する

usecase-internal/                     用途パック
  manifest.json
  hearing.json                        質問の定義（presentForm にそのまま渡せる形）
  spec/requirements.md                社内向けで決めるべき項目の雛形
  security/threats.md                 社内向けで必ず詰める点
  steps.json                          基盤の工程に差し込む、用途固有の工程
```

実行時に作業ディレクトリへ生まれるもの:

```
.blueprint/
  spec.md                             雛形の空欄を埋めた、確定した仕様
  open-questions.md                   まだ決まっていない事項
  plan.json                           工程・完了条件・止まる操作
```

工程の状態（`state.json`）は **プロジェクトの中に置かない**。セルのエージェントはプロジェクトを書き換えられるので、
そこにある `approved: true` は本物の承認と見分けがつかない。状態はサーバが持つ場所に置き、書くのは実行器だけにする。

- スキーマは zod で `common/blueprint/` に置く（画面とサーバの両方が読むため）。型は `z.infer` で導く
- 配布の形は **Claude Code のプラグイン形式に寄せる**（スキル・コマンド・フック）。mulmoterminal 以外でもスキルは動き、mulmoterminal はヒアリング画面・工程画面・止まる条件の強制を足す

## Firebase × 社内向けの中身

### ヒアリングで聞くこと（`hearing.json`）

| 項目 | なぜ聞くか |
|---|---|
| 会社の Google Workspace のドメイン（無ければメールのドメイン） | ログインを誰に許すかの根拠 |
| 利用者の規模と、役割の種類（一般・承認者・管理者 …） | カスタムクレームとルールの形が決まる |
| 扱うデータと機密度（個人情報・人事・顧客情報の有無） | 監査ログ・保持期間・リージョンが決まる |
| データの置き場所の制約（国内のみ など） | Firestore のリージョンは後から変えられない |
| 社外の人が触るか | 触るなら「社内向け」の前提が崩れるので、別の用途パックを案内する |
| 退職・異動時に何を止める必要があるか | 権限剥奪の工程の要否 |
| 既存の Firebase / GCP プロジェクト、請求先アカウントの有無 | 作成か流用か |
| 月の予算の上限 | 予算アラートの閾値 |

既存の仕様書が渡された場合は、読み取れた項目を埋めてから、空欄だけをフォームで出す。

### セキュリティで必ず詰める点（`security/`）

- **ドメイン制限は二重にかける**: 認証のブロッキング関数（`beforeUserCreated` / `beforeUserSignedIn`）でドメイン外を拒否し、さらに `firestore.rules` で `request.auth.token.email_verified` とドメインを検査する。片方だけだと、関数の設定漏れか、rules の書き漏れのどちらかで穴が開く
- **ルールは既定で拒否**。コレクションごとに開ける
- **役割はカスタムクレーム**で持ち、付与は管理者だけが呼べる関数経由にする。クライアントが書ける文書に役割を置かない
- **退職者の扱い**: Workspace でアカウントを止めても、発行済みの更新トークンは生き続ける。`revokeRefreshTokens` とクレームの削除を行う工程を用意し、ルールでは `auth_time` を失効時刻と比べる
- **監査ログ**は関数からだけ書ける別コレクションに置く。クライアントからの書き込みはルールで拒否する
- **App Check** を有効にする
- **開発用と本番用のプロジェクトを分ける**。rules のテストはエミュレータで行い、本番には触れない
- **予算アラート**を設定する（Blaze プランが必要なため、課金の確認と一緒に止める）

### 工程（`plan.json` の既定形）

| 工程 | 完了判定 | 止まる操作 |
|---|---|---|
| 前提確認（`firebase` CLI・Node・ログイン状態） | `firebase login:list` がアカウントを返す | 認証情報 |
| プロジェクト作成または選択（開発用・本番用） | `firebase projects:list` に両方ある | 課金（Blaze の有効化） |
| アプリの雛形 | `yarn build` が通る | — |
| 認証とドメイン制限 | エミュレータでドメイン外のログインが拒否される | — |
| データモデルと rules | rules のテストが通る（`@firebase/rules-unit-testing`） | — |
| 役割付与と退職者処理の関数 | エミュレータで付与・剥奪のテストが通る | — |
| 監査ログ | クライアントからの書き込みが拒否されるテストが通る | — |
| 画面 | エミュレータ接続で主要導線が動く | — |
| App Check と予算アラート | 設定が取得できる | 課金 |
| 開発用へ公開 | 開発用の URL が応答する | — |
| 本番へ公開 | 本番の URL が応答する | 本番公開 |

各工程は **判定が通るまで次へ進まない**。判定が通らない場合は、同じ工程の中で直すか、質問として止まる。

## 実行器と「止まる条件」

`state.json` の各工程は次のどれかにある:

`pending` / `running` / `awaiting-answer` / `awaiting-approval` / `passed` / `failed`

- **止まる操作は型で決める**: `billing` / `deploy-production` / `delete` / `credential`。`plan.json` の工程に宣言され、その工程に入る前に必ず `awaiting-approval` になる。AI の判断で外せない
- **質問は明示的に出す**: エージェントは実行器に質問を送り、実行器が `awaiting-answer` にする。送られない限り、実行器は止めない。エージェントが送れる出来事は質問だけ（`AGENT_EVENT_TYPES`）で、承認・回答・判定は送れない
- **読み込んだ状態は検査する**: `applyEvent` で到達できない状態（承認なしに進んだ工程、前の工程が済む前に動いた工程）は `stateProblems` が弾き、その状態からは何も進めない
- **判定は実行器が行う**: 工程の完了を AI の自己申告で決めず、`checks/` の終了コードで決める
- 実行そのものは通常のセルで動く Claude Code。実行器はそのセルに次の工程のスキルを渡し、判定を回して状態を進める

ここで決める規則（どの状態からどこへ移れるか、止まる操作を含む工程は承認なしに `running` へ行けない、など）は純粋関数として切り出し、全遷移を試験する。

## 専用画面: ヘッダーから入る別モード

**別モードに分ける**。理由:

- 非エンジニアにとってはターミナルの並ぶ画面は手がかりにならない。見るべきものは「今どの工程か・何を聞かれているか・何ができたか」
- ヘッダーから全画面の画面を開く作りは既にある（`overlayOrigin.ts` の `github` / `rooms`）。特に `rooms` は「グリッドのセルが何をしたかの記録」としてグリッドの側に置かれていて、設計図の画面も同じ位置づけになる
- **実行は通常のセルで動かし、画面はそれを見る窓にする**。同じ実行がコックピットの一覧にも出るので、エンジニアはセルを覗いて介入でき、非エンジニアは画面だけで済む。画面の側に実行を持たせると、二つの画面で見えるものが食い違う

画面の構成:

- 左: 工程の一覧と状態
- 中央: 今の工程の説明。`awaiting-answer` ならフォーム、`awaiting-approval` なら何が起きるかの説明と承認・却下
- 右（折りたたみ）: `spec.md`・差分・実行中のセルへの移動

経路は `OVERLAY_ROUTES` に並べる（名前は `blueprints` / `blueprintDetail` を仮置き）。文言は vue-i18n、スタイルは Tailwind のみ。

## 実装の順と PR の分け方

一つずつ単独で取り込め、単独で戻せる単位に分ける。

実験なので `main` には直接入れない。各 PR は実験用ブランチ `experiment/blueprint` に向けて作り、
形になった段階で `experiment/blueprint` から `main` への PR を別に立てる。

1. **パック形式のスキーマと検証** — `common/blueprint/`。`manifest` / `hearing` / `plan` / `state` のスキーマ、基盤と用途を組み合わせる純粋関数、状態遷移の規則。試験のみで画面なし
2. **Firebase × 社内向けパックの中身** — 雛形・スキル・rules・判定スクリプト。置き場所は下の「未決事項」
3. **実行器** — 状態の保持、判定の実行、セルへのスキルの受け渡し、止まる操作の強制
4. **専用画面** — ヘッダーからの経路、工程一覧、フォームと承認
5. **マーケットからの取り込み** — コレクションの Discover タブ（`importRegistry`）の作りを参考にする
