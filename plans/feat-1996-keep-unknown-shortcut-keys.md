# feat: 共有 shortcuts.json で「知らないキー」を保持する (#1996)

## 問題

`<workspace>/config/shortcuts.json` は MulmoTerminal と MulmoClaude が共有していて、**両方の
サーバがレコードを組み立て直す**（双方の `toShortcut`）。そのため、**片方が足したフィールドは
もう片方が書いた瞬間に消える**。

issue #1993 はその 1 件（MC の `color` を MT が消していた）を、フィールド名を明示することで直した。
名前を書き足す運用は、書き忘れた瞬間に同じことが起きるし、**気づけるのは消えた側のアプリを見た
人間だけ**。

## 決めたこと

| 論点 | 決定 | 理由 |
|---|---|---|
| 方針 | `toShortcut` が**認識しないキーをそのまま持ち回す** | ファイルは、それを共有する全バージョンの和集合。`serializableAppConfig`（#966）がグローバル config で同じことを既にやっている |
| 既知フィールドとの優先 | **既知が勝つ**（検証・既定値の適用結果で上書き） | 先例と同じ。壊れた `title` が素通りしない |
| 書き込み時のマージ | **しない**（読んだものを持ち回すだけ） | ファイルから消えたフィールドを、こちらが「保持」の名目で**復活させない**。最後に書いた側の内容が正 |
| プロトタイプ汚染 | `Object.fromEntries` で組み立てる | `__proto__` を代入するとオブジェクトが再親付けされ、そのキーが JSON から消える（#966 のコメントが指摘している罠） |
| 型 | `Shortcut` は既知の形のまま。組み立てはスプレッドで、返り値は `Shortcut` | `Shortcut` に index signature を足すと、全コードでタイポが合法になる |
| MulmoClaude 側 | **この PR では触らない。issue を立てる** | 向こうも同じ組み立て直しをしているので、こちらの新フィールドは向こうで落ちる。対称に直して初めて完全になる |

## 実装

- `server/backends/shortcuts.ts` — `toShortcut` が、既知キー以外を先にスプレッドしてから既知キーを
  重ねる。既知キーの一覧は 1 箇所（`KNOWN_SHORTCUT_KEYS`）に置き、型から外れないようにする。
- `common/shortcuts.ts` — 「この型はファイルが持ち得るものの**部分集合**であって、知らないキーは
  素通りする」ことを契約として書く。
- `test/server/backends/shortcuts.spec.ts` —
  - 知らないキーが normalize を通り抜ける。
  - 既知キーは検証結果が勝つ（壊れた `title` が素通りしない）。
  - **GET → PUT の往復でディスクに残る**（実際に効く経路）。
  - `__proto__` を含むファイルでプロトタイプが汚染されない。

## やらないこと

- MulmoClaude 側の変更（issue を立てる）。
- クライアント側は変更不要 — `isShortcut` はフィルタで、オブジェクトをそのまま通す。`reconcile` も
  スプレッドで既存フィールドを保つ。
