**状態**: 提案（着手前）
**日付**: 2026-08-12
**前提**: [`docs/shared-app-principles.md`](../docs/shared-app-principles.md)（不変条件）と
[`plans/feat-shareable-collections.md`](./feat-shareable-collections.md)（D1–D10 と実装順）

この計画が答える問いは 1 つだけである:

> **宣言で書けないことが増えて、真実が HTML に移っていくのをどう止めるか。**

止め方は「HTML を禁じる」ではなく（原則 11）、**宣言の表現力を広げ続ける**ことしかない。
以下の優先順位はすべてその基準で並んでいて、「あると便利」では並んでいない。

## 現在地 — ルールが実際に強制している語彙

新しいものを足す前の基準線。すべて `../mulmoserver/firestore.rules` に入っていて、
2026-08-12 時点で本番に deploy 済みである（mulmoserver #155 / #156 / #157）。

| 領域 | 語彙 |
|---|---|
| 身元 | `idFrom: auto \| auth.uid \| auth.uid+field`、`emailField` |
| 認証段階 | `auth: none \| anonymous \| verifiedEmail` |
| 役割 | `owner` / `editor` / `viewer` / `participant` / `assignee`（コレクション単位の上書きあり） |
| 行スコープ | `assigneeField`（書きのみスコープ、読みは全部） |
| 投稿 | `createFields`、`selfUpdate[status]`、`selfTransitions[status]`、`finalize`、`submitOnly`、`audience` |
| 状態機械 | `statusField`、`transitions`（`initial` を含む）— create も writer も縛る |
| 期限 | `window.fromMs` / `untilMs`、`window.fromField`（別レコードの epoch millis を見る） |
| 順序 | `stampField`（create でサーバ時刻に固定、以後不動） |
| 可視性 | `public.read`、`participantRead`、`peerVisibility`、`revealGated` + `gatedFrom` / `revealBy` |
| ライブ | `session/current` と `gateOn`（phase + current の一致） |
| 検証 | `validate.required`、`validate.keyFields`（**最大 2 キー**） |
| 完全性 | `immutable` |
| 副作用 | `mail`（`on[template].from`/`to`、`toField`、`dataFields`）— **遷移そのもの**に束縛 |
| 入口 | `/a/{slug}`（公開）、`/m/{slug}`（ロールを持つ人）、`/p/{slug}`（participant）。予約は削除不可 |

ホスト側（MulmoTerminal）にあるのは **init / fork / check / preview / invite / publish / unpublish**
（`SHARED_APP_ACTIONS`、`server/infra/shared-app-tool.ts`）と、その門番（移行ゲート、フィールド名検査、
公開入力検査）。門番は診断であって権限ではない（原則 2）。`deploy` は**無い** — staging と一緒に
撤去され、その場所に立っているのが `preview` である（`plans/feat-shared-app-no-staging.md`）。

**ビューの宛先は 3 つある**（当初「2 つしかない」と書いていたが、member / roster が入った）:
公開の `config/*`、ロールを持つ人の `apps/{aid}/member/*`、名簿の人の `apps/{aid}/roster/*`
（`appViews.ts`）。中身は `.claude/skills/<slug>/views/` に書いた custom ビューか、公開だけは
宣言から生成したフォーム（`config/public` への射影、`publicForm.ts`）。
**ここが一番痩せている場所であり、真実が HTML へ漏れる圧力が全部かかる場所である。**

## 0. 決定済み・未実装（先にこれ）

[`plans/done/feat-shared-app-public-view.md`](./done/feat-shared-app-public-view.md)（#1658、マージ済み）の
3 つ。レビューを 20 件通した設計で、**この計画はそれを前提にする**。要点だけ:

1. **`idFrom: "field"` + `idIn` + `window.untilField`** — 枠 id を予約の id にして、
   排他をドキュメント id の衝突にする。`idIn` は**必須**（省略を許すと実在しない枠を名乗れる）。
   排他に関わるキーは live なレコードが 1 行でもあれば**凍らせる**
2. **公開ページのカスタムビュー** — 親が Firebase を持ち、ビューは `window.__MC_PUBLIC_VIEW` だけを読む。
   ホスト用の `__MC_VIEW` とは**別の契約**で、両対応のアダプタは作らない。
   `event.source` の検証では足りず、**親が自分で描いた確認**を挟む
3. **salon テンプレート**の更新

**この 3 つを終える前に下の拡張へ進まないこと。** 2 は公開側の唯一の描画経路になるので、
以降のビュー型はすべてその上に載る。

## 1. `schedule` ビューを一級の宣言にする（最優先）

**なぜ最初か。** 「シフト − 承認済み予約 − 所要時間 = 空き枠」は、レコード単位の計算では書けない。
書けないまま美容室を作ろうとすると、**その計算は HTML に移る** — 原則 11 が壊れる最短経路であり、
しかも最初に必ず来る要求である。

```json
{
  "type": "schedule",
  "resource": "stylists",
  "availability": "shifts",
  "busy": { "collection": "bookings", "when": "status == 'approved'" },
  "slot": { "durationFrom": "services.duration" },
  "submit": "bookings"
}
```

「リソース × 時間 × 所要時間 × 予約」は業種を跨いで繰り返し現れる（会議室、設備、面談、貸出）。
**1 つ作れば何度も効く**し、これを打てるかどうかが「コードを書かずに」が本当かどうかを決める。

設計上の注意:

- **描画は宣言、排他はドキュメント id**（0 の 1）。ビューは空き枠を*見せる*だけで、
  「取れた」と決めるのは create の衝突である。ビューの計算を権限と読み違えないこと
- **公開側とメンバー側で同じ型を使い、読めるものだけが違う**。公開側の枠行に個人情報を
  載せない（原則 5）
- ホスト側の custom ビューと公開ビューで**2 つの実装を持たない**。0 の 2 の経路に載せる

## 2. 条件表示（skip logic）

「Q3 が『はい』なら Q4 を出す」。アンケートで `schedule` と同じ役割を果たす —
これが無いと分岐は HTML へ行く。

**線は「完全なスクリプトではなく単純な式」に限ること。** 既存の `when` / `fieldBase` を条件表示に
使い、多段になっても式の形を保つ。ここは表示だけの話であって権限ではない
（隠したフィールドは送れる。送らせたくないなら `createFields` から外す — それが強制側である）。

## 3. 公開の集計を、3 つの別物として分ける

「集計」を 1 つの機能として足すと必ず壊れる。ルールは数えられず（原則 3）、
フィールドを隠せない（原則 5）からである。分けるべき 3 つ:

| | いつ使えるか | 誰が更新するか |
|---|---|---|
| **読み手の集計** | 読者がその行を全部読んでよいとき | 誰も。読んだ側が数える |
| **原子的な鏡** | 権威の書き込みと同じバッチで更新できるとき | 書いた本人。ルールが `getAfter` で両側を要求する |
| **射影** | 読者が元の行を**読めない**とき（アンケートの総数） | 固定のプラットフォーム効果。アプリのコードではない |

**アンケートの「回答は見せずに集計だけ見せる」は 3 番目にしか置けない。** 1 番目で書くと
個票が公開され、2 番目で書くと回答者に他人の集計を書く権限が要る。
3 番目に手を出すまでは、**「集計は出せない」と言う**のが正しい（原則の最後の節）。

## 4. 名前付きデータセット

ビューが Firestore のクエリを組み立てるのをやめ、宣言された名前を受け取る。
コレクション / 対象読者 / 絞り込み / 並び / 上限 / ライブか / 参照の展開まで。

publish 時に**クエリ計画の検査**ができるようになるのが本命である:

- その対象読者がそのコレクションを読めるか（読めないビューは publish 前に分かる）
- 公開側の無制限読み取りを拒否する（匿名トラフィックのコスト、原則 1 の 4）
- 複合インデックスの要否を挙げる
- **絞り込みを権限と読み違えていないか**（絞り込みは表示、権限はルール）

## 5. 能力のバージョンを、**どこかに記録する**

今は記録が無い。`mulmoserver` に CI は無く、**ルールの deploy 状態はどのリポジトリにも
残らない**（唯一の記録が `feat-shareable-collections.md` の実装順 7c の一文である）。

新しいキーを足すたびに、著者には成功に見えて訪問者は壊れたページを見る状態が作れてしまう。
必要なのは 2 つ:

- **deploy されたルール／ランタイムの能力を読める場所**（`apps` の外の 1 文書で足りる。
  ルールの deploy と同時に手で書くのでも、無いよりはるかに良い）
- **publish がそれを見て拒否すること**。「古いルールでは fail closed」は既存アプリを守るだけで、
  **新しく publish したアプリを守らない**

これは機能ではなく、**上の 1–4 を安全に出すための前提**である。1 と同時か、その前に。

- ~~**`selfDelete`**~~ — **実装済み**（2026-08-13、[`feat-shared-app-self-delete.md`](./feat-shared-app-self-delete.md)）。
  本人が自分のレコードを消し、枠がその場で開く。ルールは `deleteWith` の 1 枝で熱いパスに

- **添付（Storage）** — 親レコードに紐づく権限。**Storage ルールから `firestore.get()` が

  「繰り上がりました」を**送れる**ようになる（今は繰り上げは計算のたびに現れて消える）

## 適合の判定は、既にあるシナリオで行う

新しい例題を並べない。`feat-shareable-collections.md` には**充足状況**の節が 4 つある:

- 美容室（S1）— 1 と 0 が入って初めて満たされる
- Web アンケート（S2）— 2 と 3 の「射影」が要る
- オンライン授業（S3）— ライブと段階的公開。ビュー側が残り
- 議会投票（S4）— 記名投票は満たされている。秘密投票は**やらない**

**増やすなら、その節を更新すること。** 別の場所に別の一覧を作ると、片方だけが古くなる
（CLAUDE.md の #1097 と同じ失敗の形）。テンプレートも同じで、
`server/skills/mulmoterminal-shared-app/templates/` の `salon.md` / `gym.md` に足す。

## リポジトリ横断の順序

能力ごとに、この順で出す。**順序は正しさの一部**である。

1. **mulmoserver のルール + emulator テスト** — 受け入れて強制する
2. **mulmoclaude core** — 著者の構文を解析し、ルールが読む形へ射影する
3. **mulmoserver のランタイム** — その射影を読んで描く
4. **mulmoterminal** — 検査し、staging へ書き、publish し、報告する
5. **テンプレートとスキル** — 3 と 1 が本番に出てから初めて書き始める

2 つ、忘れやすい事実:

- **1 は手で deploy する。** CI は無い。「マージした」は「出た」ではない
- **公開ビューを伴う能力は mulmoserver が先。** 古い公開ページは新しい宣言を読めず、
  訪問者は「記入するものはありません」を見る。**publish した本人には成功に見える**

## やらないこと

- **アプリごとのサーバコード / Cloud Functions**（D8）
- **秘密投票**（表示で隠すのは秘密投票ではない）
- **任意区間の重なり判定** — 離散的な枠 id に限る
- **公開ページに 2 本目の描画経路**（素朴な `public.read` の表と宣言ビューの併存）
- **ホストで動く監視・定期処理**（原則 1）
