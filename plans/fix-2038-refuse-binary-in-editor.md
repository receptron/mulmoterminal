# #2038（前半）— バイナリをエディタに流し込まない

## なぜ分けたか

issue #2038 は 3 つの部品からなる:

1. サーバがファイルを OS の既定アプリへ渡す経路（`POST /api/files/open`）
2. **プレビューできない型をそう表示する**（今は文字化け）
3. クリックの行き先をペインに寄せる（今は突然ダウンロード）

**2 だけが、今日すでに起きているデータ破損**を含む。1 と 3 を待たせるべきではないので、
2 を先に出す。1 + 3（「OS で開く」ボタンと導線）は続きの PR。

## 実測した破損（報告者は未確認としていた）

324 バイトの xlsx をペインで開いて書き戻すと:

```
元 324 bytes → 書き戻し後 336 bytes / バイト列は同一でない
zip として開けるか: いいえ — BadZipFile
```

**破損は「読み込み時」に起きている。** `bytes.toString("utf8")` が不正バイト列を U+FFFD に
置換するので、**1 文字打っただけで、打った箇所ではなくファイル全体が壊れる**。

さらに `storeBackup` は**その壊れたテキストの方**を保存していた。安全網が破損版を記録していた。

## 判定は「UTF-8 として往復できるか」

`server/files/editableText.ts` の `losslessText(bytes)`。往復して同じバイト列に戻るかを見る。
**往復そのものが失う操作**なので、これが失われるかどうかの厳密な判定になる。

古典的な「NUL を見てバイナリ判定」は**両方向に間違える**:

| 入力 | NUL 判定 | 往復判定（正しい）|
| --- | --- | --- |
| `a\0b` | バイナリ（拒否）| **編集して安全** — 往復で不変 |
| Latin-1 の `café` | テキスト（通す）| **壊れる** — NUL を含まない |
| xlsx（zip）| 中身次第 | **壊れる** |

答えないのは「読めるか」。UTF-16 のテキストは往復できるが文字化けして見える。これは表示の
問題で、この関数は破壊の問題を見ている（コメントに明記）。

## 適用範囲

`/api/files/browse/text`（エディタ）と `readTextOr4xx`（rendered ビュー）の**両方**。
同じ読み方で同じ被害が出るので、サイトではなくクラスで直す。

`MAX_EDIT_BYTES` のコメントは元から "Large/binary files are refused rather than streamed into
a textarea" と言っていた。実装されていたのはサイズの半分だけだった。

## ペイン側

415 を**失敗ではなく面**として受ける。エディタは隠す — 中身のあるファイルの上に空の
バッファを見せるのは保存への誘いで、その保存が破壊そのものだった。

## 検証

- 実サーバで 415 と、ファイルが無傷であること、**バックアップも作られないこと**を確認。
- 実ブラウザで面が出ること、エディタが隠れること、テキストに戻すと面が消えることを確認。
- 反転 mutation 3 種: 判定を常に通す（3 件赤）/ NUL 判定に替える（**4 件赤**）/ 拒否を
  バックアップの後に置く（1 件赤）。
