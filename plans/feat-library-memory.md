- 本文は wiki と同じ描画（`renderWikiHtml`: frontmatter を落とし、`[[name]]` をリンクの span に、marked のあと DOMPurify）。同じプロジェクトに無い名前のリンクは押せない形にする

## 二つ目の PR（健康診断）

- 規則は純関数（`server/backends/library/memory-health.ts`）。ディスクに触るのは読み手（`memory-health-read.ts`）だけで、そこも記憶が挙げたパスが「あるか」を聞くだけで中身は読まない
- 規則: `MEMORY.md` が読み込み上限を超えている / 記憶があるのに `MEMORY.md` がない / `MEMORY.md` が挙げるファイルがない / 記憶が `MEMORY.md` に載っていない（`MEMORY.md` が読めないときは言わない）/ frontmatter の `name`・`description`・`type` の欠け（`type` は `metadata` 下でも最上位でも）/ その名前の記憶がない `[[リンク]]`（コードの中は数えない）/ 挙げたファイルが無い
- 「挙げたファイル」はコード表記（`` `server/foo.ts` ``）の中で、スラッシュ（または `\`）と 1〜12 文字の拡張子があり、名前に使う文字は英数字・`_` `.` `-` `+` `@` `~` だけ、スキームもワイルドカードも空白も無いもの。広げすぎると命令や文が「無いファイル」として出るので、取りこぼす方を選んでいる。`@` で始まるもの（パッケージ名）は除く。`~/` はホーム、絶対パスはそのまま、相対はそのプロジェクトのディレクトリで解く。ディレクトリが分からない相対パスは判定しない。最上位のフォルダがこのマシンに無い絶対パス（`/sche_b1.cgi` のようなサイトのパス）も判定しない
- 実データで試した誤検知（パッケージ名、サイトのパス）は規則から外した。残ったものは本当に移動・削除されたファイル
- 画面: 一覧の上に「n 件を整えられます」と「見る」（整えられるものだけに絞る）、行頭の小さな点、プロジェクトの見出しの下に索引の問題、読む画面に問題を一文で
- 健康診断の結果は一覧とは別に取り、一覧を待たせない

## 三つ目の PR（編集）

削除（ごみ箱と取り消し）・統合は次の PR。

- 編集するのはファイルの本文そのもの（frontmatter ごと）。知らない frontmatter の項目は、書き戻しで消えようがない。ファイル名は変えないので `MEMORY.md` は触らない
- 保存は、開いたときの本文（その SHA-256）のままのときだけ。エージェントは作業しながら記憶を書くので、開いたあとの変更の上には書かず、409 で「変わったので保存しなかった」と言う（編集内容は残し、「読み直す」を出す）。確かめてから書くまでの間が残る隙
- 書けるのは記憶フォルダの記憶ファイルだけ（slug と名前を Claude Code の形で確かめる）。リンクは書かない（`readBoundedText` が読まない）。無くなったファイルは作らない（それも 409）。256 KB まで
- 編集を始めると、そのプロジェクトで動いているセッションがあれば警告する（再開の確認と同じ `readResumableList` の `runningKey`）
- 画面: 読む画面の右下に「編集」（`Enter`）。編集中は本文の場所が入力欄になり、`⌘Enter` で保存、`Esc` でやめる（ライブラリは閉じない）。保存すると一覧と健康診断を読み直す
- 実データには書かない。確かめは別の作業用 HOME の、作った記憶で行った

## 四つ目の PR（削除: ごみ箱と取り消し）

統合・作業コピー間の統合・出所は、それぞれ別の PR にする（どれも単独で戻せるため）。

- 動いているセッションがあるときは、編集と同じく警告にとどめ、読むだけにはしない（2026-11-20 に決定。設計の原則4は記憶については警告と書き換える）
- 削除はマシンのごみ箱へ移す。ファイル画面の削除と同じ `moveToTrash`（`rename` なので別のボリュームなら動かさない）。確かめの画面は出さず、取り消しのある知らせを出す
- 移すのは、開いたときの本文（版）のままのときだけ。変わっていたら移さない（409）
- `MEMORY.md` はそのファイルへリンクしている行だけを消す。行末はそのまま。`MEMORY.md` が無ければ触らない。読めない・忠実に読めない `MEMORY.md` があるときは、食い違いを作らないよう削除しない
- 移したあとに `MEMORY.md` の書き込みが失敗したら、ファイルを元に戻す
- 取り消しはサーバーが覚えている（id だけを返す。要求はパスを持たない）。戻すときは、同じ名前のファイルができていたら上書きしない。`MEMORY.md` が自分の書いたままなら元の本文に、そのあと変わっていたら消した行を末尾に足す（もう載っていれば足さない）
- 取り消しを覚えておくのは一定時間とサーバーが動いている間だけ。過ぎてもファイルはごみ箱に残り、手で戻せる
- 一つのファイルの保存・削除・取り消しは、このサーバーの中では順番に一つずつ（ファイル、次に `MEMORY.md` の順で待つ）
- 画面: 読む画面の `more_horiz` に「ごみ箱へ移す」。会話の読む画面と同じメニューを部品（`LibraryMoreMenu.vue`）にして共有する

## 五つ目の PR（統合）

作業コピー間の統合・出所は、それぞれ別の PR にする。

- 統合は、同じプロジェクトの記憶 A を記憶 B へまとめること。読む画面の `more_horiz` →「ほかの記憶に統合する」で、同じプロジェクトのほかの記憶を読む画面の中で選ぶ（`Esc` で読む画面に戻る）
- 選ぶと B を読み、B の本文の末尾に A の本文（frontmatter を除く）を足した状態で編集が開く。どうまとめるかは人が編集で決める（AI による統合案は #3334）
- 保存すると、B に書き、A を削除と同じ手順でごみ箱へ移して `MEMORY.md` の A の行を消す。A と B のどちらも、開いたときの版のままのときだけ（変わっていたら何もせず 409、どちらが変わったかを返す）
- 順番: B の版を確かめ、A をごみ箱へ（削除の手順そのまま）、B に書く。B に書けなかったら A を戻す
- 取り消し一つで両方を戻す: A を戻して `MEMORY.md` の行も戻し、B が統合で書いたままなら元の本文に戻す。そのあと B が変わっていたら B はそのまま（両方の本文が残る）
- 一つのファイルの変更は、このサーバーの中では順番に一つずつ。複数のファイルを扱うときは、ファイルを名前の順に、そのあと `MEMORY.md` の順で待つ。どの変更もこの順なので、二つが互いを待つことはない
- 統合は下書きを残さない（一度の操作で、やり直すならもう一度選ぶ）
- A を指す `[[name]]` リンクは書き換えない。名前の記憶がないリンクは健康診断が出す（次の PR で書き換えるようにした）

## 六つ目の PR（統合でリンクを書き換える）

決めたこと（2026-11-21）:

- 統合では、A を指す `[[リンク]]` を B へ書き換える（統合した本文の中も、プロジェクトのほかの記憶も）。何件書き換えるかは保存の前に見せる
- 取り消しでは、書き換えたリンクも戻す。ただし、そのあと変わった記憶はそのまま

作り:

- 対象は、A のファイル名（`.md` を除く）か frontmatter の `name` を指す `[[…]]`。向け先は B の `name`（`[[…]]` に入らない名前なら B のファイル名）。A と B が同じ名前を持つときは、その名前のリンクは B に届いているので書き換えない
- コードの中（コード表記とコードの塊）は書き換えない。どこがコードかは健康診断と同じ marked の字句解析で決める。字句解析が返すコードを、元の文の中の位置に戻せないファイルがあれば、何も書かずに断り（422）、そのファイルを挙げる。行末がすべて `\r\n` のファイルは `\n` にして調べて戻す。行末が混ざっていてコードがあるもの、UTF-8 として読めないもので A へのリンクがあるものは断る
- 統合は、始めたときにフォルダにある記憶すべての順番を、名前の順に、そのあと `MEMORY.md` の順で待つ（保存・削除と同じ並び）。調べてから書くまでの間に、同じサーバーの保存が割り込まない。書き換えるのはその記憶だけで、あとからできた記憶は順番を取っていないので触らない
- ほかの記憶は一つずつ書く。途中で失敗したとき、まだ書いている途中のものが戻したあとに書き込まないため
- 順番: B の版を確かめる → 書き換えを決める（断るならここで） → A をごみ箱へ → B を書く → ほかの記憶を書く。途中で書けなかったら、それまでに書いたものをすべて戻す
- サーバーは書いた本文を返す（統合した本文の中のリンクも書き換わるため）。画面はそれを表示する
- 件数は `GET /api/library/memory/:slug/:file/links?from=…` で、統合と同じ処理を B の今の本文に当てて数える

## 六つ目の PR（作業コピー間の重複）

一本化の操作（ほかの作業コピーへ写す・取り込む）は次の PR。これは見つけて知らせるところまで。

- 同じリポジトリの作業コピーは、ディレクトリの `origin` が同じリモートのもの（`resolveRemoteForge`、ホストとパスを小文字にしてそろえる）。worktree も同じリモートなので同じリポジトリになる。リモートが無い・分からないフォルダは数えない

- 規則は純関数（`memory-workcopies.ts`）。読み手はフォルダごとに記憶の版（本文の SHA-256）だけを残し、全部読んでから判定する（全部の本文を抱えないため）
- リモートの問い合わせは一つのディレクトリにつき 60 秒覚えておく（ライブラリを開くたびに全部へ git を走らせないため）
- 実データ（読むだけ）で、mulmoterminal の作業コピー 2〜6 に同じ名前の記憶がそれぞれ見つかり、どれも本文が違った
