# スキルが効いているかを測って残す（#3438）

下敷きは https://singularitysociety.org/articles/blog/2026-11-23-model-or-skill/ の「効いているかの確かめ方」。同じ課題をスキルありとなしで3回ずつ解かせ、合格か不合格かで数え、差をばらつきと比べる。費用は失敗込みの合格1件あたり。スキルが読まれなかった合格は数えない。使うべきでない課題を1つ入れる。

PR は一つにした。測る仕組み、課題を作る同梱スキル、画面は一緒に正しいか一緒に間違うかのどちらかで、分けると同梱スキルが案内する「測る」ボタンが無い状態が出荷される。

- 測る仕組み: 課題の形式、実行、採点、まとめ、保存、HTTP
- 課題を作る同梱スキル `mulmoterminal-skill-eval`（プランモードのセルで開く。承認まで書かない）
- 画面: スキル画面の各スキルの下に「効いているかを測る」。課題を作る、測る（回数と費用の上限を出してから）、進み具合と停止、結果、前の結果

## 実行の場（試して決めた）

`claude -p` を、毎回新しい一時フォルダで、`--setting-sources project` 付きで走らせる。

- このとき、利用者の `CLAUDE.md`、`~/.claude/skills`、プラグイン、フックは読まれない（試した: 利用者のスキルは一覧に出ず、`CLAUDE.md` の規則にも答えられなかった）
- 費用が下がる。同じ書き込みの課題で、既定は 0.11 ドル、こうすると 0.019 ドル（haiku、1回）。フックが足す文脈と、プラグインのスキルの一覧が無くなるため
- 「あり」はそのフォルダの `.claude/skills/<slug>/` にスキルのフォルダを写す。「なし」は写さない。比べる二つの違いはスキルがあるかどうかだけになる。`--disallowedTools "Skill(<名前>)"` で止める案もあったが、止めた側にもスキルの説明が一覧に残り、モデルが呼ぼうとして拒否されるので、こちらを取った
- 利用者の環境そのままではない。記事は「自分の道具で測る」ことを勧めるが、費用と再現性を取った。道具は Claude Code そのものなので、道具の違いは入らない
- プラグインのスキルも、フォルダの中に写してから測る。名前は slug になる
- 書き込みは `--permission-mode acceptEdits` で許す（試した: 一時フォルダに書けた）。コマンドの実行は、課題の組が `allowedTools` で許したものと、スキル自身が frontmatter の `allowed-tools` で許すもの。後者は利用者がふだんスキルを使うときにも効くので、測る場でも同じにする（測るのはふだんの挙動）。拒否されたものは記録に残す
- スキルのフォルダは、実行の始めに一度だけ一時フォルダへ写し、各回はそこから写す。実行中に `SKILL.md` を直しても、記録した中身と違うものを測らない
- 1回の上限は `--max-budget-usd`。時間の上限で止める

## 読まれたか

`--output-format stream-json --verbose` の行から、`Skill` の道具呼び出しで `input.skill` が測るスキルの slug のものを探し、その呼び出しの `tool_result` がエラーなしで返ったときだけ「読まれた」とする（試した: 成功した呼び出しには `tool_result` が返った）。拒否された呼び出しは読まれていない。最後の `result` の行から費用、最後の返事、拒否、失敗を取る。

## 採点

課題ごとに一つ。

- **コマンド**: 一時フォルダで `/bin/sh -c` で走らせ、0 で終われば合格。設計図の `runCheck` を使う。コマンドは利用者が承認したファイルにあるもので、リクエストからは来ない
- **点検項目**: 別の `claude -p` が、一時フォルダのファイルと最後の返事を読んで判定する。採点の前に `.claude/skills` を消す。残すと採点役が測っているスキルを読み、それを基準に採点してしまう。道具は `Read Glob Grep` だけ。`--json-schema` で `{ pass, reasons }` を返させる（試した: `structured_output` に入った）。返事の中の「書きました」は信じず、ファイルを見るように指示する。採点の費用は別に数える

## 課題の組の形式

`~/.mulmoterminal/skill-evals/<フォルダ>/cases.json`。フォルダ名はスキルの名前で、`:` は `__` に変える。フォルダのスキル（プロジェクトの `.claude/skills`）は slug だけで実行されるので、二つのプロジェクトの同じ名前のスキルが混ざらないよう、プロジェクトのディレクトリのハッシュを `@` のあとに足す。課題を作るセルには、保存先のフォルダをそのまま渡す。課題に使うファイルは、隣の `files/<課題の id>/` に置き、実行ごとに一時フォルダへ写す。

- `kind: "use"`: スキルが効くはずの課題。ありとなしで `repeats` 回ずつ
- `kind: "avoid"`: スキルを使うべきでない課題。ありだけで `repeats` 回。スキルを呼ばず、採点にも通れば合格
- 「あり」の頼み方では、スキルの名前を出す（記事: 名前を出さないと読まれる率が半分ほどに落ちる）。「なし」と「avoid」では出さない

## まとめ方（`common/skillEvalSummary.ts`、純関数）

- 合格率は use の課題だけで、腕ごとに。「あり」の合格は、スキルを呼んだものだけを数える。呼ばずに合格した数は別に出す
- ばらつき: 「なし」の各回（1回目・2回目・3回目）の合格率の最大と最小の差
- 判定:
  - 差がばらつきより大きく、かつ課題1つ分（`repeats` 回分の合格）以上 → 効いている（負なら逆効果）。合格率は割り算なので、ちょうど課題1つ分の差が浮動小数の誤差でわずかに足りなくなる（0.6 - 0.4）。小さな許容幅で比べる
  - それ以外 → 差がある証拠なし
  - どちらかの腕が一度も終わっていない → まだ判定できない
- 合格1件あたりの費用 = その腕の費用の合計（失敗込み）÷ 合格数。合格が0なら出さない
- use の課題が少ないときは、そのことを出す（記事: 45題では13点の差も見えなかった）

## 保存

- 実行ごとに `runs/<id>.json`。測ったときの `SKILL.md` の中身とハッシュ、課題の組のハッシュ、モデル、各回の結果、まとめ
- 1回終わるごとに書き直す。サーバーが途中で止まった記録は「途中で止まった」と読む
- 同時に走らせるのは一つのサーバーで一つの評価だけ

## 確かめたこと

- 実物の `claude`（haiku）で、課題3つと使うべきでない課題1つを2回ずつ: 14回、約1分40秒、採点込みで約0.42ドル。判定は「効いている」（あり 83%、なし 0%）。ありの1回は名前を出したのにスキルを読まず不合格で、読まれた率に出た
- 使い捨ての HOME のサーバーで、画面から「測る」→ 確認 → 進み具合 → 結果まで。14回、約2分半、0.46ドル。一時フォルダは残っていない
- 課題を作るセルを開く経路は、偽の起動で確かめただけ（本物のセルは開いていない）
