# 改善案を測るとき、スキルなしの結果は起点の測定から写す（#3465）

## 目的

改善案の実行は、スキルありとスキルなしの両方を測り直していた。スキルなしの試行はスキルの文を読まないので、改善案が何を変えても結果の条件は変わらない。測り直しは費用の無駄で、改善案と今のスキルの比較も、別々の「なし」に揺られる。

## 決めたこと

1. 改善案の実行が測るのは、スキルありの試行だけ（`improveOrder`）。「使うべきでない」課題もスキルありで測る
2. スキルなしの試行は、改善案のもとにした測定（`isBaselineFor` を満たす実行）から写す。その測定は同じ課題の組で完了したもので、モデルは組の中にあるので、条件は同じ
3. 写した試行は `reusedFrom` に元の実行の id を持つ。ここで測った試行は空
4. 写すのは改善案を書けたあと。書けなかった実行には何も写さない（測ったものが何もないので）
5. 「この評価にかかった費用」は、その実行が自分で測った試行と採点、改善案を書く費用だけ（`runSpentUsd`）。合格1件あたりの費用は写した試行の費用で出す（その結果を得るのにかかった費用なので）
6. 押す前に出す回数と費用の上限（`improveAttempts`、`maxImproveCostUsd`）、進み具合の分母と分子は、実際に測る分だけ
7. ふつうの「測る」では使い回さない。前の測定から時間が空くと、Claude Code やモデルの更新で結果が変わり得る

## やらないこと

改善案を自動で何度も繰り返すこと。費用が増え、同じ課題に合わせ込む度合いが増し、人が確かめる場面が減る。
