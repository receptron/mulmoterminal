# fix: Windows CI が半々で落ちる — レンダーの予算が実測と合っていない (#2018)

## 事実

- 落ちるのは `test/server/infra/shapescriptRenderTool.spec.ts` の **pixel 系 4 本だけ**、
  いずれも **ちょうど 15,000ms**（＝ `vitest.config.ts` の `testTimeout` 既定）。
  ファイル全体の 60,035ms はその 4 本の合計。
- main の Windows: `f44cb14d` ✅ → `f41db779` ✅ → `86a47f5e` ❌ → `1d2275ff` ❌。
  PR ブランチでも 1 回落ちて re-run で通った。**タイミングの崖**であって壊れてはいない。
- Windows ランナーには**ブラウザがある**ので、ファイル冒頭の probe が成功し pixel ケースが走る
  （ubuntu / macOS ジョブでは probe が失敗して丸ごと skip されるので、そもそも走らない）。
- プラグインは **1 コールごとに Chromium を起動して閉じる**
  （`@mulmoclaude/shapescript-plugin/dist/render.js`: `launch(...)` … `finally { close() }`）。
  つまり 4 ケース = コールドスタート 4 回 + ソフトウェア GL（`--use-gl=swiftshader`）。
- 実測（macOS・warm）: **1 ケース ≈ 1.0 秒**。Windows では 15 秒で終わらない。GPU 無し・
  コールドスタート・遅いディスクで 15 倍は説明がつく。壊れている兆候は無い。

## 直し方

**予算を実際のコストに合わせる。** タイムアウトを伸ばすのは「遅いのを隠す」ことではなく、
**この 4 本だけが本物のブラウザを起動している**という事実を明示すること。

| | 決定 | 理由 |
|---|---|---|
| タイムアウト | pixel ケースに `RENDER_TIMEOUT_MS = 60_000` を明示 | 観測された 15s 超に対して 4 倍の余裕。ブラウザの無いホストでは skip されるので、この予算が使われるのはレンダーが実際に走る場所だけ |
| ケース数 | inline レンダーの 2 本を **1 本に統合** | 2 本目は同じレンダーに「絶対パスか」を訊いていただけ。Chromium 1 回ぶん（≈1s、Windows では 15s+）を丸ごと節約でき、失うアサーションは無い |
| プラグイン側 | **触らない** | ブラウザの使い回しは上流（`@mulmoclaude/shapescript-plugin`）の話。ここで小細工しない |
| CI で skip する案 | **採らない** | Windows は現状**唯一 pixel を実際に検証している場所**。緑にするために消すのは、この 4 本の存在理由を消すこと |

## 検証

- 手元: 7 本 green、4.49s（統合前は 8 本 6.20s）。1 ケース ≈ 1.0s は変わらず。
- **Windows は手元で回せない。** この PR の `test_windows` ジョブが検証そのもの。
