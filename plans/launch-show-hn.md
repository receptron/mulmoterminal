## 1. ポジショニング — 「2 枚目のターミナルから効く」（最初に読む）

**一言。**

> Vibe coding にターミナルは 1 枚で足りる。**足りなくなるのは、2 枚目からです。**

**中核の主張。** MulmoTerminal は AI エージェントを *使う* ツールではなく、
**複数のエージェントを *監督する* ための計器盤**である。競合はすべて「エージェント 1 体との
対話体験」を良くする方向に投資していて、「N 体を同時に走らせたとき人間の注意をどう配分するか」を
正面から扱っているものがない。ここが唯一の非商品化領域。

**本当の課題は注意力ではない。** 同じ見た目のペインが N 個あると、**人間が N 個のコンテキストを
頭の中に保持しなければならない**。色分け・名前バッジ・状態の枠・cockpit roster は、それを
頭から画面に移す装置。README の「What people say after switching」がすでにこれを言語化している
（別のエージェントのターミネルに返信を打ち込んでしまう、6 分割すると 4,000 字の返答が読めない、
IDE を 6 枚開くと 64GB のマシンが詰まる）。**この 3 つが Show HN 本文の骨。**

### 最重要 — 対象読者の広さで勝負しない

競合カテゴリ（エージェントオーケストレーション基盤）は「10 体並列」を前提にするので対象が
数百人に絞られる。MulmoTerminal は **2 体目から効く**。README がすでにこう書いている：

> **You don't need ten agents for this to pay off.** Users have reported the switch being worth it
> at **one to three** parallel sessions.

**これを本文の中盤に置く。** 「10 体回してる人向けでしょ」で読者が自分を対象外に分類するのが、
このカテゴリの最大の離脱要因。先回りして潰す。

### 先頭に立ててはいけないもの（2026 年にはコモディティ）

- **ブラウザターミナル / PTY / Electron でないこと** — 実装上の判断であって価値ではない
- **Canvas（MCP によるリッチ出力）単体** — リッチ出力はもう珍しくない。**必ず並行監督と結びつける**
  （「10 セルを走査するとき、テキストの壁よりカードの方が速く読める」）
- **コスト / トークン表示、テーマ、Skill メニュー** — あると良いが乗り換え理由にならない
- **「AI で開発が速くなる」系の主張全般** — HN で最も嫌われる型

## 2. Show HN の投稿フィールド

### タイトル（HN 上限 80 字）

- **本命:** `Show HN: MulmoTerminal – a grid for running Claude Code and Codex in parallel` **(77)**
- alt A: `Show HN: A browser grid for running many Claude Code and Codex agents at once` (77) — 製品名を落とす版
- alt B: `Show HN: MulmoTerminal – see which of your parallel AI agents needs you` (71) — 課題側から入る版

本命を選ぶ理由: HN のタイトルは**何であるかを平叙で言う**のが最も強い。`grid` は物理的な
比喩で誤解の余地がなく、`Claude Code and Codex` が対象読者を一撃で自己選択させる。
alt B は魅力的だが、`needs you` が製品の中身を説明しないまま感情に寄るので Show HN では弱い。

**URL:** `https://github.com/receptron/mulmoterminal`（ドキュメントサイトではなく **repo**。
Show HN の読者はまず README とコードを見る）

### 本文（投稿と同時に、自分でコメントとして投稿する）

構成を固定する。**5 段落・500 語以内・機能列挙をしない。**

1. **課題（自分の実体験として）** — Claude Code を 2〜3 個並列で回し始めた瞬間に起きたこと。
   別のエージェントに返信を打ち込む、どれが自分を待っているか分からない、IDE を複数開くと重い。
2. **やったこと** — サーバ側に PTY を置き、ブラウザのグリッドに並べた。セルの枠の色が状態
   （working / 入力待ち / 完了・未読 / idle）。**入力待ちだけが鳴る**。
3. **意外だった設計判断を 1 つ**（HN が食いつくのはここ） — 候補は §7 の「PTY を選んだ理由」。
   API ラッパではなく本物のターミナルを飼っているので、`claude --resume` も既存 transcript も
   そのまま動く。移行作業がゼロ。
4. **正直な限界**（§6 の免責と同じもの。**必ず本文に書く。コメントで言わされたら負け**） —
   Windows は tmux がないので永続化が落ちる、`gh` 前提で GitHub 以外に広げられていない、
   6 週間前に始めたものなので荒い。
5. **CTA** — `npx mulmoterminal@latest`、MIT、ローカル完結（テレメトリなし）、
   フィードバック歓迎。

**書いてはいけないもの:** 「revolutionary」「game-changer」「10x」、機能の箇条書き 10 行、
ロードマップ、資金調達の話、他製品との比較表。

### ファーストコメントに置く GIF

`docs/guide/images/hero.gif`（グリッドが状態ごとに色を変えながらリアルタイムに動く）を
README 冒頭に置いてあるので、**repo を開いた瞬間に見える**。Show HN では本文より先にこれが効く。
→ ゲート条件（§5）に「hero.gif が現行 UI と一致していること」を入れる。

## 3. キーメッセージ（順位付き。この順で、この数だけ）

1. **状態が見える。** working / 入力待ち / 完了・未読 / idle が枠の色。入力待ちだけがチャイムを鳴らす。
   → *画面外で詰まっているエージェントを取りこぼさない。*
2. **多数を見ることと、一つを読むことがトレードオフでなくなる。** グリッド ↔ 拡大。
   拡大しても cockpit roster が全員をテキスト 1 行で保持する。
3. **エージェントに依存しない。** Claude Code / Codex / Antigravity を同じ計器盤に並べられる。
   → 上流ベンダのどれもが構造的に作れないもの。**これは今期いちばん大きい変化なので、必ず入れる。**
4. **消えない。** tmux でサーバ再起動・クラッシュ・`node --watch` を跨いでセッションが生き残る。
   既存の `claude --resume` がそのまま来るので、移行作業がゼロ。
5. **離れられる。** 完了・入力待ちでスマホに Web Push、RemoteHost からタップで yes/no/continue。

**予備（FAQ でだけ使う。先頭に出さない）:** git worktree とワンクリック PR、コスト/トークン表示、
Files ペイン、Canvas、per-directory テーマ、設定を書く skill 群、Docker サンドボックス、
`claude-ollama`。

### まだ言語化されていない第 2 の軸（本文で 1 行だけ触れる）

直近の #910 シリーズで、**ターミナルの隣に「人間が確認・介入する作業面」**ができた
（file explorer / エディタ / オートセーブ / 外部変更検知 / **条件付き保存でエージェントの
書き込みを上書きしない**）。「人間とエージェントが同じファイルを同時に触る」前提の設計で、
ここには他にない固有性がある。ただし**まだ主張にするには早い** — 本文では
「エージェントが触っているファイルを、隣で安全に開いて直せる」と 1 行だけ書き、
食いついたコメントに §7 で答える。

## 5. ゲート条件 — 日付ではなく、これで決める

**なぜ日付を決めないか。** Show HN は再投稿が効かない一発勝負で、**初回体験が壊れていると
そこで終わる**。いま未クローズの issue には、初回体験を直撃するものが実際に残っている
（#725 = 別レポで新規セッションを始める導線が分かりにくい、#1152 = 自動リロード後に通知音が
鳴らず完了通知が失われる、#782 = スクロールバーが出ない）。**通知が鳴らないのは、この製品の
主張そのものが成立しないという意味**なので、これを抱えたまま出すことはできない。

### 出す条件（全部満たすこと）

- [ ] **#1152 が解決している。** 「入力待ちで鳴る」は本計画の主張 #1。ここが不確かなら他は全部無意味
- [ ] **#725 が解決している。** 「別のリポジトリで 2 つ目を始める」が初回体験の核。ここで詰まると
      製品の主張（並列）に到達しないまま離脱する
- [ ] **#782（スクロールバー未表示・ドラッグ選択）** が解決しているか、既知として README に明記
- [ ] **まっさらなマシンで `npx mulmoterminal@latest` → グリッドに 2 セッション** までを、
      macOS と Windows で 1 回ずつ通しで実施し、詰まった箇所を全部記録した
- [ ] **`hero.gif` が現行 UI と一致**している（古い UI の GIF は「もう使われてない製品」に見える）
- [ ] **Show HN 本文が書けている**（§2 の 5 段落。当日に書かない）
- [ ] **§7 の想定質問に、全部答えが用意できている**（HN はコメント欄が本体）
- [ ] **60 秒動画**（PH / X 用。HN だけなら不要だが、副次チャネルを同日に打つなら必須）

### 出す日

条件が揃った最初の **火・水・木** の **米国東部 08:00〜10:00（= JST 21:00〜23:00）**。
月曜は競合が多く、金〜日は滞留が少ない。**JST 21 時開始は、当日 4〜6 時間の返信対応を
日本時間の夜に収められる**という実務的な理由もある。

**MulmoClaude の PH（8/4）との関係。** 同日・同週を避ける。理由は注意の分散ではなく
**返信対応の体力**で、どちらもコメント欄の初動が結果を決めるため、1 人が両方は回せない。
条件が 8/4 週に揃った場合は、**MulmoTerminal を後ろに送る**（PH の方が日付固定の制約が強い）。

## 7. 想定質問と答え（HN はコメント欄が本体）

**「tmux + iTerm の分割でいいのでは？」**
→ 分割は *表示* の問題を解くが *状態* の問題を解かない。6 枚のペインは全部同じ見た目で、
どれが自分を待っているかは自分で読みに行くしかない。ここは枠の色とチャイムが教える。
加えて 6 分割は 1 枚あたりが読めなくなる（4,000 字の返答が事故になる）ので、
グリッド ↔ 拡大の往復が要る。

**「なぜ Electron でなくブラウザ？」**
→ サーバに PTY があり、ブラウザは単なる表示。だから **別のマシンやスマホから同じセッションに
届く**し、IDE を N 枚開いたときのメモリ爆発が起きない（64GB が詰まったという報告がある）。

**「なぜ API ではなく PTY？」（最も食いつかれる論点。§2 の第 3 段落に使う）**
→ 本物の `claude` プロセスを飼っているので、`claude --resume`・既存 transcript・skill・
hooks・MCP 設定が**そのまま**動く。移行作業がゼロで、上流が機能を足した日にこちらも使える。
API ラッパは初日は速いが、上流の変化のたびに追随コストを払い続ける。

**「テレメトリは？データはどこへ？」**
→ ローカル完結。セッションは自分のマシンの PTY、設定は `~/.mulmoterminal/config.json`。
スマホ通知を使う場合だけ中継が入る（**この点は正確に説明する。曖昧に「ローカルだけ」と
言わない**）。

**「Claude Code 依存では？上流が同じものを出したら？」**
→ すでに Claude Code / Codex / Antigravity を同じ計器盤に並べている。上流の各社は
**構造的に自社エージェントしか並べられない**。残るのは個々の機能ではなく、
worktree・push・永続化・監督 UX の統合。

**「エージェントが触ってるファイルを自分で開いたら壊れないの？」**
→ 条件付き保存で、エージェントの書き込みを人間の保存が上書きしない。外部変更は検知して知らせ、
編集は 3 世代バックアップを持つ。

**「Windows は？」**
→ 動くが tmux のネイティブビルドがないので永続化が落ちる（プレーン PTY にフォールバック）。
CI で Windows を回している。**ここは正直に、聞かれる前に本文に書く。**

**「GitHub 以外は？」**
→ 現状 `gh` 前提。抽象化は棚卸し済みだが未着手（#981）。

## 9. 成功指標

Show HN の成果は star ではなく、**入ってきた人が使い続けたか**で測る。

| | 最低ライン | 良い | 出典 |
|---|---|---|---|
| HN フロントページ滞在 | 到達する | 上位 10 位 | — |
| HN コメント | 20 | 60+ | — |
| GitHub star（T+7d） | 72 → **250** | 600+ | `gh repo view` |
| npm DL（launch 週） | 平常の 3 倍（〜25,000/週） | 10 倍 | npm API |
| **npm DL（T+21d の日次）** | **launch 前（〜800/日）を上回って定着** | 2 倍で定着 | 同上。**これが本命の指標** |
| launch 由来の issue | 5 件以上（＝実際に使われた証拠） | — | `gh issue list` |

**star は指標にしない。** 6 週間で 72 star の製品にとって、star は「見た人の数」であって
「使った人の数」ではない。**T+21 日の日次 DL が launch 前より高い**ことだけが、
ローンチが人を連れてきたのか、通り過ぎただけなのかを分ける。
