# ライブラリの索引の基盤（#3328、親 #3327）

ライブラリの全機能が使う索引を作る。画面は作らない（#3329）。デザインは `docs/library-design.md`。

## 置き場と形

- `~/.mulmoterminal/library/index.db`（`node:sqlite`）。索引は元データの写しにすぎないので、消せば次の読み取りで作り直す。形の版が変わったときも捨てて作り直す
- 同じ `HOME` で複数の MulmoTerminal が動く（このマシンでも常に複数）。全部が同じ DB を使い、索引を作るのは **一つだけ**: DB の `lease` 行を期限つきで取ったプロセスが作り、進捗もそこに書く。ほかのプロセスは読むだけ
- 表
  - `files` — ファイルごとの「どこまで読んだか」（大きさ、更新時刻、読んだ位置、途中の畳み込み状態）
  - `conversations` — 会話ごとの要約行。形は全エージェント共通で `agent` 列を持つ。最初は claude だけ
  - `turns` — 全文検索。FTS5 の `trigram`（日本語を語に切らずに引ける）。2 文字以下の語は `LIKE` の全走査になる

## 何を入れるか

- 要約行: タイトル（`/rename` > `aiTitle` > 最初のプロンプト）、cwd、ブランチ、PR（`pr-link`）、金額と増減行数（最後の `cost-state`）、最初と最後の時刻、使われたスキル（`attributionSkill`）、フックのエラー数、サブエージェントか（と親の会話）、一時パス由来か、ユーザーの発言数
- 全文検索: ユーザーの発言と返答の本文だけ。道具の入出力、注入されたテキスト（`<command-…>` など、`isInjectedPrompt` と同じ判定）、`isMeta` は入れない。一発言は先頭から上限文字数まで
- `~/.claude/history.jsonl` のプロンプトも `turns` に入れる。会話記録に残らない、実行中に打ったプロンプトがあるため（`prompt-history.ts` の説明どおり）
- 一時パス由来のプロジェクト（OS の一時ディレクトリ配下の cwd）は要約行だけ入れて本文は入れない。このマシンではプロジェクトの大半がこれで、検索の雑音になる。容量（#3333）は要約行で足りる
- サブエージェント（`<session>/subagents/*.jsonl`）も要約行と本文を入れ、親の会話の id を持たせる

## 差分だけ読む

- 既存の `forEachJsonlRecordIn`（バイト範囲の畳み込み）と同じ考え方: 前回読み終えた位置から追記分だけを読む。最後の書きかけの行は数えない
- 縮んだ、または同じ大きさで書き直されたファイルは、その会話の行を消して最初から読み直す
- 消えたファイルの要約行と本文は消す。ただし、すべてのディレクトリを読めた走査で、かつまだ `lease` を持っているときだけ（読めなかったディレクトリのファイルは「消えた」のではない）
- 読むのは、読み始める前に測った大きさまで。読んでいる間に足された分は次の走査で読む。途中で止まったファイル（大きさは同じでも最後まで読んでいない）は続きから読む
- 読んだ分は一定の件数ごとに確定する（一つのファイルにいくら発言があっても、溜めておく量は件数で上限がある）。各回の確定は「どこまで読んだか」の更新と要約行・本文の追加を一つのトランザクションにし、次の記録が始まる位置で区切る。書き込む時点で、まだ `lease` を持っていて、かつ読み始めた位置が DB の値のままのときだけ確定する（最初から読み直す場合も同じ）。どちらかが動いていれば別のプロセスが先に進めたので捨てる
- ファイルは一度だけ開き、大きさ・中身・先頭のハッシュを同じハンドルから取る。読んでいる最中にパスが別のファイルに置き換わっても、混ざらない。続きから読むのは、先頭と、前回読み終えた位置の直前のバイトが、どちらも前回と同じファイルのときだけ（置き換えられた・書き直されたファイルは最初から）。両端を残して途中だけ書き換えた場合は見分けられないが、会話記録は追記しかされないので、全体を読み直してまで確かめることはしない

## 画面を止めない

- 索引の DB は **専用のワーカースレッド** だけが開く。作るのも検索するのもそこ。サーバーのメインスレッドはメッセージを送って答えを JSON のまま返すだけ
  - 理由は実データで測った: `node:sqlite` は同期で、初回の走査はメモリも大きく揺らすので、メインスレッドで動かすとファイルの切れ目で処理を手放していても、数秒の止まりが何度も出た（大きな会話の前後）。メインスレッドには全部の端末が乗っている
  - サーバーは常に `tsx` で動くので、ワーカーも `.ts` をそのまま読む
- ワーカーはライブラリの API が最初に呼ばれたときに起こす（起動時には起こさない。開かない人に CPU を使わせない）。死んだら次の呼び出しで起こし直す。答えない呼び出しは時間切れで 503
- 索引作りは API が呼ばれるたびに、前回から一定時間たっていれば裏で走査し直す。ファイルは一つずつ、行は流しながら読む

## API

- `GET /api/library/status` — 進捗（作っているか、何件中何件、最後に終えた時刻）
- `GET /api/library/conversations` — 一覧。`cwd` の絞り込み、一時パスとサブエージェントは既定で除く、新しい順、`offset` / `limit`
- `GET /api/library/conversations/:id` — 1 件の要約
- `GET /api/library/search?q=` — 会話ごとに一件、一致した発言の抜粋つき。タイトルも対象

## 純関数にするもの（試験で壊れた入力まで通す）

- 1 行を要約の状態に畳む処理と、1 行から検索用の本文を取り出す処理
- `history.jsonl` の 1 行
- 一時パスかどうか
- 抜粋の切り出し、`LIKE` の特殊文字の逃がし

## 決めたこと

- 全文検索の範囲は発言と返答の本文まで（issue の推奨どおり）
- 一時パス由来の会話は本文を入れない
- 索引作りは最初の API 呼び出しで始める

## 本物のデータで分かったこと

`scratchpad` のスクリプトでメンテナの `~/.claude` 全体から索引を作り、時間・イベントループの止まり・DB の大きさ・検索の速さを測った（スクリプトは PR に入れていない。測り方は PR 本文に書く）。そこで直したもの:

- **同期の処理がイベントループを止める。** 上の「専用のワーカースレッド」はこれへの答え。そのうえで、 別のプロセスのロックに当たった書き込みは `busy_timeout` のあいだ同期で待つ（読み取りは WAL なので待たない。別プロセスで確かめた）。ワーカーの中でも答えが遅れるので、待ちは短くし、諦めた書き込みは次の走査でやり直す
- **読めなかったファイルを「消えた」と扱っていた。** ロックや読み取りの失敗でも会話が索引から消える。消すのはファイルが本当に無いとき（`ENOENT`）だけにした
- **ファイルごとの完全な同期書き込みが初回を遅くしていた。** 索引は作り直せる写しなので `synchronous = normal` にした
- **よく出る語の検索が遅かった。** 一致した発言を全部会話に結んでから並べていた。一致した会話を先に絞ってから結び、抜粋は表示する会話の分だけ取り直す形にした。タイトルにも trigram の索引を張った（会話の行は upsert にして、置き換えで古いタイトルが索引に残らないようにした）

残る性質:

- 1〜2 文字の検索と、ごくありふれた語の検索は、3 文字以上の普通の語より遅い（前者は trigram が使えず全走査、後者は一致が多すぎる）。ワーカーの中なのでサーバーは止まらない。画面側で入力の間引きをする（#3329）
- DB は元の会話記録よりずっと小さいが、ギガバイトの単位になりうる。大半は全文検索の索引。容量（#3333）で見えるようにする
