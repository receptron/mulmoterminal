# fix: dev-server がポート衝突で無限再起動する (#1735)

## 症状

2 つ目の clone で `yarn dev` すると、ポート 34567 が埋まっているためバックエンドが起動できず、
`scripts/dev-server.mjs` が **3〜4 秒ごとに永久に再起動**し続ける。1 プロセスあたり CPU 113〜117%。
気づかず放置した結果、load average が 75〜80 まで上がった（停止後 13.9）。

vite 側は生きていて `/api` は 1 つ目のバックエンドにプロキシされるので、**ブラウザ上は正常に見える**。

## 真因

スーパーバイザのバックオフ判定が **「速く落ちたか」だけ**を見ていて、**「何度も落ちているか」を
見ていない**。

```js
const ranFor = Date.now() - startedAt;
if (ranFor < FAST_CRASH_MS) {        // 2000ms
  delay = Math.min(delay * 2, MAX_DELAY_MS);   // バックオフ
} else {
  delay = MIN_DELAY_MS;                        // 250ms に戻す
}
```

**バックエンドはポートを bind する前に重い初期化を全部やる。** `server/index.ts` は 1003 行あり、
`server.listen()` は **939 行目** — help docs のシード、skill の同期、codex へのミラー、
スケジューラ登録 25 件が全部その前。結果、起動〜死亡が **約 3 秒 > `FAST_CRASH_MS`** になり、
毎回 `else` に落ちて **指数バックオフが一度も発動しない**。

実測（修正前、20 秒間）:

```
[dev-server] backend exited (code 75) — restarting in 250ms
[dev-server] backend exited (code 75) — restarting in 250ms
[dev-server] backend exited (code 75) — restarting in 250ms
```

`after Nms` も `(crash loop? …)` も付いていない = `if` 側を通っていない直接的な証拠。

## 直し方

issue の案 A（bind を先に）は **1003 行のうち 938 行を動かす**ことになるので採らない。
代わりに **B（終了コードで分岐）と C（連続失敗回数）**を入れる。どちらも純粋関数にする。

`scripts/dev-server-config.js` に `restartPlan()` を追加（既に `shouldSchedule` などが
純粋関数として置かれていて、`.d.ts` と spec が揃っている場所）。

- **exit code 75（ポート使用中）は再試行しない。** 再試行しても直らないうえ、毎回
  「ユーザーの home にファイルを書く副作用のある初期化」を走らせてしまう。停止して理由を出す。
  **ファイル保存では再挑戦する**（それが唯一の復帰経路なので、メッセージにもそう書く）
- **それ以外は連続失敗回数で倍々にする。** `runFor` は判断に使わない。遅いクラッシュループも
  クラッシュループ。

カウンタを 0 に戻す経路は 2 つ。**経過時間はどこにも使わない。**

1. **バックエンドが listen したと報告したとき。** `server/index.ts` の listen コールバックから
   `process.send({ type: "listening" })` を出し、スーパーバイザは `stdio` に `ipc` を足して受ける
2. **ファイル変更による意図的な再起動のとき**（`killedForRestart`）。編集は開発者による「直した」の
   意思表示なので、失敗の連続はそこで切れる。ポート衝突で停止したあとの唯一の復帰経路でもある

送信は `process.connected` で守る。**親が切断したあとも `process.send` は関数のまま残り、呼ぶと
`ERR_IPC_CHANNEL_CLOSED` が非同期に飛んで uncaughtException でプロセスが死ぬ**（実測）。`?.` でも
try/catch でも止まらない。スーパーバイザに Ctrl+C を打った直後、バックエンドがまだ 3 秒の初期化中
だと踏む。CodeRabbit の指摘で、実験して確認してから直した。

### 最初「5 秒以上生きたら成功」にしていて、Codex に指摘された

`HEALTHY_MS = 5000` を置いていたが、それは **この PR が「経過時間は誤った指標だ」と言って直した
ものを、閾値を上げただけで再導入していた**。listen 前の初期化が 5 秒を超えるマシン（または後段の
初期化失敗）では、毎回カウンタが戻って 250ms 固定の永久ループになる。

指摘を受けてから実測して確認した — listen 前に 6 秒かけて失敗するスタブで、修正前は
`restarting in 250ms` が延々と続いた。まさに直したはずの症状。

## 検証

**スタブだけで済ませない。** スーパーバイザは全開発者が通る経路なので実機で回す。

| 確認 | 修正前 | 修正後 |
| --- | --- | --- |
| ポート衝突（issue の再現手順、20 秒） | 起動 3〜5 回 | **起動 1 回** |
| 遅いクラッシュ（3 秒生きて exit 1） | 250ms 固定 | **250 / 500 / 1000 / 2000 / 4000** |
| ポート衝突後にファイル保存 | — | **再挑戦する** |
| **実機 `yarn dev`**（ポート 34567 が実際に埋まった状態、45 秒） | — | **重い初期化 1 回、以降停止** |

負の対照: 旧挙動を復元すると新テスト 3 件が赤、戻すと 15 件全緑。

### 実機で拾ったもの（1）

`delay` 変数を消したのに `onChange()` の 105 行目に代入が残っていて、**ファイル保存の経路が
`ReferenceError` で落ちた**。純粋関数のテストでは絶対に出ない。「ファイル変更で再挑戦できる」と
自分でコメントに書いた直後に、その経路が壊れていた。

## 範囲外

**bind を先にする（issue の案 A）はやっていない。** 副作用のある初期化を起動できないのに走らせる
問題自体は残る。ただし今回の修正で「起動できないなら 1 回で止まる」ので、実害は 1 回分に縮む。
`server/index.ts` の初期化順の整理は別の変更。

## 副産物として見つけたフレーク（別 issue）

作業中に `yarn test` が 4 回に 1 回落ちた（`google.spec.ts` の `socket hang up`）。単体では
0/25 で、#1729 と同じ負荷依存のクラス。**supertest が内部で ephemeral port にリスナーを張る**
ためで、`grep 'listen('` では 0 に見える。#1729 のとき「実ソケットを立てる spec はこれ 1 本だけ」
と書いたのは誤りだった。該当 19 本を #1737 に切り出した。この PR の diff の外。
